# Coordinating agents in Herdr

This guide works on its own in a host where `herdr` is available. It does not install agents, configure the host or create panes by default. If `herdr` is missing, or there is no access to an authorized session, explain the precondition and stop: do not attribute started tasks or results to a pane you could not observe.

## Scope and boundaries

- Ask for the goal, the repository or working directory, the read and write limits, the agent type and the allowed effects. Read only what you need from the pane and from the authorized checkout; do not copy credentials, private transcripts or out-of-scope files into prompts or reports. Write only to authorized destinations, and make clear which agent will make each change. Do not make commits, publications or irreversible changes on the person's behalf.
- Check the installed help before acting: `herdr agent --help`, `herdr pane --help`, `herdr tab --help` and `herdr <group> <subcommand> --help` for the chosen operations. Options, agent types and model/effort gestures vary between hosts; the agent's screen confirms the effective values, not the launch argument or an assumption about the profile.
- If several agents share files or a stateful resource, agree on ownership and write order; serialize only the stretch that needs it, with a generic mechanism suited to the context. Do not invent a global lock or manage other people's agents.
- A request for permission, a spend of quota/resources, a commit, a publication, an irreversible change or wider access goes back **verbatim to the person**, with its context and every visible alternative. Wait for an explicit written answer to **that** request; do not choose or press keys on their behalf, do not infer authorization from earlier instructions, and do not delegate it to the blocked agent. If the person does not answer, keep the block. Relay only the option they authorized, then check its receipt and the state that follows. A general authorization given earlier ("answer the routine ones yourself") is not the answer to **that** request. The host's permission policies still apply: if the host blocks sending keys or prompts to another agent's dialog, do not look for another way; summarize for the person the question, its options and the agent's recommendation, and let them answer in their pane.

## Observable cycle

1. **Locate.** Use `herdr tab list`, `herdr pane list` and, if an agent exists, `herdr agent list`/`herdr agent get <target>` to find the right tab/pane. Use `herdr tab get <id>` or `herdr pane get <id>` before acting if there is ambiguity. Create a tab (`herdr tab create`) or split a pane (`herdr pane split`) only once the destination and the layout are agreed; do not close or replace other people's panes. To split a tab evenly between N agents, remember that `--ratio` sets the fraction the split pane keeps: the first cut goes at 1/N, the next at 1/(N-1) on the new pane, and so on. Check the layout with `herdr pane layout` and fix it with `herdr pane resize --direction <direction> --amount <ratio delta>`. Keep the task ↔ pane relationship; do not rely only on an agent name.
2. **Start.** In an authorized pane with a free interactive shell, check `herdr agent start --help` and the type (`--kind`) actually available. Use `herdr agent start <name> --kind <type> --pane <id>` with only the agent options its help confirms. Success means detection and interactive readiness in that pane, not that the task has started. If the pane is busy or the type is not supported, stop and rethink the choice; do not force the process.
3. **Verify before the handoff.** Read `herdr pane read <id> --source visible` or `herdr agent read <target> --source visible` and compare the agent's banner or indicator, the effective model and effort, the session and the readiness with the agreed task. A narrow pane truncates the banner: read it with the layout already fixed or with `herdr pane zoom <id>` (and undo the zoom afterwards). If you adjust model or effort through that agent's own UI, wait for it to update, read the screen again and only then confirm. If they are not shown or they differ, report the uncertainty and ask before using a different configuration.
4. **Delegate.** Send a bounded task with goal, relative path or destination, read/write limits, expected test and stop conditions; `herdr agent prompt <target> "<task>"` accepts the send. `--wait` can wait for a later state, but it does not identify the turn: if the agent was already working, it may match the end of another task. Never take "prompt accepted" as "read", "run" or "finished"; read the pane again to check that it received **this** task. If receipt is uncertain, inspect before resending, to avoid duplicate instructions.
5. **Follow.** `herdr agent wait <target> --until working --until idle --until blocked --until done --timeout <ms>` waits for observed states; use a suitable timeout and read afterwards with `herdr agent read <target> --source recent` or `herdr pane read <id> --source visible`. A timeout, an unknown state or a pane that does not change proves neither failure nor success; record what you observed and reassess. `herdr pane wait-output` serves one specific visible signal, not to credit the whole task.
6. **Close the task, not the pane.** On `done` or `idle`, read the screen anyway: it may hold a question, a permission or an error. Check the task's deliverable and validation against the evidence in the checkout or the agent's output. Report what is complete, what is unverified and what is pending; do not attribute to the person an approval they did not write.

| Observed signal | Next action before reporting |
|---|---|
| `working` | Wait or read progress; do not interrupt or send a second uncertain instruction. |
| `blocked` | Read the pane, take the question and its options to the person and wait for a specific authorization; confirm receipt after relaying it. |
| `idle` | Read the pane: it may be waiting on a question or the next task; check the previous result before concluding. |
| `done` | Read the pane and verify the deliverable/tests of that specific task before declaring it concluded. |
| `unknown` | Read the pane, review detection (`herdr agent explain`) and keep the state as uncertain; do not repeat or declare success. |

## Questions, restarts and recovery

- On a block, read the full text of the request and present its alternatives to the person with the effect of each one. Do not run `herdr agent send-keys`, `herdr pane send-keys` or `herdr agent prompt` to answer until you receive the explicit choice. `herdr agent prompt` rejects sends to an agent that is already blocked: after the written choice, use the keys needed from `herdr agent send-keys <target> <key>` or `herdr pane send-keys <id> <key>` as the visible dialog requires, without selecting another alternative. Read the screen again and, if receipt is not confirmed, keep the question pending without assuming the answer arrived. An answer sent right before a disconnection is also uncertain.
- A dialog with several tabs is read in full before taking it to the person: walk through it without choosing (navigation keys vary between hosts) and read the screen again after each key, because the refresh may arrive late. When relaying authorized choices, send only when the review screen shows every answer; if one is missing, complete that tab before sending.
- After a restart or a session change, agent names may be lost. Relocate with `herdr tab list`/`herdr pane list` and the pane identifier you kept; use `herdr pane get <id>` and `herdr pane read <id> --source visible` to check it is the expected session and task. `herdr agent get <id>` or `herdr agent explain <id>` clarify detection. Do not send "continue" or repeat the task until you have checked what the instance received and what it ran; if that cannot be shown, ask the person how to recover.
- If the pane changes, does not reflect the model/effort after the pause, another instance appears or the evidence contradicts the state, stop, inspect and report the uncertainty. An authorization for one question does not carry over to another, even if they look alike.

## Synthetic examples

- **Blocked:** an agent asks "publish now? Yes / No". Take both options to the person. With the written answer "No", relay "No", read the screen again to check receipt and keep the result without claiming a publication.
- **General authorization:** the person said earlier "answer the routine ones yourself", and an agent asks to accept a route proposal. That does not answer this request: summarize the proposal and its options, ask for the choice and, if the host blocks sending keys, let the person answer in their pane.
- **Uncertain send:** `prompt` accepts "review module", but the screen still shows the previous task. Read the pane and wait for a sign of receipt; do not resend blindly or declare the review finished.
- **Restart:** `agent get <name>` no longer resolves. Find the associated pane and read its screen; resume following only after identifying the instance and the last task.
- **Model:** after selecting another variant or effort, the banner still shows the previous one. Wait and read again; until it reflects the change, do not report the new value as effective.
- **Finished:** `done` appears and the screen reports an output path and passing tests. Check that path and the test output in the authorized checkout; only then report that task as complete.
